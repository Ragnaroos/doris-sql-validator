# 逐 Case 归因报告模板

每条非匹配、非源端负向查询保存为 reports/attribution/cases/<batch-id>/<case-id>.md，沿用 YAML/验证 JSON 的编号。匹配及默认排除的负向不另建文档，用户明确纳入的负向专项注明理由。本文前半是 Case 模板，后半是批次汇总模板；实际生成时分别保存，不把所有查询拼成一份长报告。

只写真实事实。不得生成额外 SQL、执行 JSON 或 evidence/ 目录；工具返回结果直接整理到本 Case 文档中。大结果仅列完整比较范围、行数、有限样本或反例，不整表复制；错误保留实际原文。使用中文解释状态，代码与错误原文保持不变。

# <case-id>：用一句话描述具体问题

## 1. 结论与处理建议

- 具体原因：SQLGlot 缺少/错误生成了什么，或为什么当前属于 Doris/框架/环境问题；不只写“语义不同”。
- 是否需要修改 SQLGlot：需要 / 不需要 / 尚不能确定，并给理由。
- 进度：原因已定位 / 调查未完成 / 前提阻断 / 尚未开展。
  原因已定位只表示有证据解释当前差异，不是全部输入同义证明；调查未完成表示仍缺关键确认；前提阻断写明数据/权限/输出/工具等具体问题；尚未开展不能写成已完成归因。
- 已确认范围、关键限制和下一步。
- 对应修复任务编号（有实际任务才填写）。

## 2. 源查询与首轮问题

完整源 SELECT；源文件/语句编号/行号、同文出现序号和 .out 对应回显位置。引用批次汇总的 YAML、准备材料与共同环境，记录本 Case 特殊数据阶段、类型域或 Session 条件。

给出源 .out 的成功结果/错误依据、SQLGlot 实际生成的完整 Doris SQL 或完整转译错误，以及首轮具体错误/字段/行数/行值差异。没有生成 SQL 就不伪造 SQL；读取失败不推测源 SQL 非法。

## 3. 独立候选与实际执行

将完整候选 SQL 写入 sql 代码框，解释改写依据。保留实际命令（含 --candidate-sql，必要时用标准输入）、执行时间、SQLGlot/数据库版本与会话，明确是否与社区输出相同；相同只算重跑。

| 尝试 | 是否实际执行 | 修改要点 | 执行状态及具体错误/差异 | 结果能支持什么 |
| :--- | :--- | :--- | :--- | :--- |

逐次说明失败尝试，不覆盖为最后的成功结论。保留被采用候选及重要失败候选的完整 SQL。没有执行时说明确切原因，省略不适用的候选细节，不虚构“通过”。

实际事实来自 probe-pg-case 或 probe-pg-batch 的返回值，不由模型推测。批量时保留请求序号与本 Case 的对应关系，可采用 --output-format markdown 的对应事实片段，整合到本节及分维度比较中，不另存工具报告或在每个 Case 重复粘贴整批输出。记录行数、关键字段类型、完整结果是否取得、实际错误原文和反例；不只抄“匹配”。若结果超过工具上限、被截断或归一化失败，应写信息不足，不能把样本当完整验证。共同代码依据和规则解释链接汇总任务/待补证条目，本 Case 仍写明适用条件和例外。

原 .out 与本次实时 PostgreSQL 的关系要明确；不一致时说明数据阶段/Session/版本前提，不能无声地换掉源基线。工具未自动完整校验这件事时也如实写出。

| :--- | :--- | :--- | :--- |

| 行数 | | | |
| 行值和重复次数 | | | |
| 要求的最终顺序 | | | |
| 重复执行稳定性 | | | |

仅用相同 / 不同 / 信息不足 / 未执行 / 不适用，并解释依据。类型未知不算通过；类型不同仍检查行值。无最终 ORDER BY 按多重集合比较，保留重复次数；有 ORDER BY 不假定排序键唯一。Float 不擅自放宽容差，Decimal 不用近似比较掩盖精度差异。

## 5. 代码依据与具体归因

实际 SQLGlot 提交、文件/函数/必要行号，说明 Parser、AST、Doris Generator 或继承行为如何导致差异。区分 Doris 的直接能力、行为差异、可条件补偿和尚未找到安全模拟；一个失败候选不证明绝对无法实现。

如果属于框架/驱动、数据/Session 或读取问题，写明确切依据和处理去向，不强行列为 SQLGlot 补丁。候选当前行值相同不等于已确认可通用迁移的转换规则。

## 6. 修复方案与验收要求

链接批次汇总中的 task 详细条目；共同修改方案、PR 边界和验收要求集中写在那里，本节只补该 Case 的适用性、例外及剩余问题。同一 Case 可以关联多个 task，同一 task 可以关联多个 Case。

| 关联 task 与汇总章节链接 | 本 Case 中对应的具体问题 | 阶段/类型/版本前提及验收观察 | 其他独立问题或未满足条件 |
| :--- | :--- | :--- | :--- |

有依据才提出 SQLGlot 修复；证据不足则说明下一步，链接汇总的待补证事项，不安排“照抄候选”。标明本 Case 哪些错误应由本任务消除、哪些完整结果仍依赖其他任务。Case 全部匹配与单项任务验收分开，不能为使本 Case 通过而把无关改动混入任务。

不修改原 SQL/.out、基表或全局比较策略来制造通过。严格错误兼容边界单列授权/关联理由，不要求复制全部源端报错。

## 7. 已测边界与限制

| 变体目的 | 完整源变体/目标候选 SQL | 实际执行情况 | 类型/值/顺序/错误结论 |
| :--- | :--- | :--- | :--- |

边界通过 --source-variant-sql 明确传文本，真实执行 PG，不能借原 .out。把 SQL 和实际结果写在本 Case 文档，不另建文件。未执行、未覆盖和只验证某条共享规则都明确，不宣称全部参数或完整类型域通过。

# 批次汇总报告模板

保存为 reports/attribution/<batch-id>-attribution-summary.md。它是用户与修复 Skill 的总入口，链接 Case 文档，不展开全部 SQL/错误和执行结果，不另生成独立修复清单。

面向未参与执行过程的使用者，以中性、通用的报告标题组织内容。以下统计从本批全部验证 JSON、准备材料与逐条调查事实取得，不固定示例文件名、数值或阶段数，不引用个人问答和操作历史。已有报告不因更新模板而自动覆盖。

## 1. 执行摘要

用简短段落概述输入脚本的主要测试内容、纳入范围、首轮匹配率、已发现的主要问题、可进入 SQLGlot 修复的方向与关键限制。明确执行到归因还是已修复；本 Skill 不实施代码修复。数字应与后文一致，不用“已生成文档”替代“已完成归因”，不将全部不匹配统称 SQLGlot 缺陷。

## 2. 输入与覆盖范围

列出批次、原 SQL/.out、验证 JSON、YAML、数据准备 Markdown 与双端准备 SQL 的路径，以及 SQLGlot 提交、数据库版本/Session 和类型映射限制。多阶段按实际范围提供导航，不另建索引文件；密码不入文档，单 Case 的环境例外写入对应文档。

| 覆盖项目 | 实际范围/数量 | 统计口径或证据限制 |
| :--- | :--- | :--- |
| 输入脚本及测试内容 | | 依据源 SQL 概述语法/函数类别，不暗示覆盖全部 PostgreSQL SELECT |
| 验证查询记录 | | 按原文每次出现计数；阶段间核对 Case ID 不重复，说明导入异常记录是否计入 |
| 不同 SQL 文本与重复出现 | | 有实际统计才填，说明采用的文本识别规则；未统计则注明，不作语义去重 |
| 数据状态与执行分组 | | 单状态或多个 stage；依据准备材料说明对象/数据/会话变化及查询对应关系 |
| YAML 与验证 JSON | | 实际文件数量和命名范围；一份 YAML 对应一次 run，不将阶段数乘以全批查询数 |
| 未纳入或证据缺失范围 | | 普通 DDL/DML 跳过、查询提取遗漏、输出读取异常分别说明，不与接受数直接相加 |

数据核验次数、实际对照次数和边界变体数不是原查询数。不要在导入遗漏或输出不足时宣称完整脚本全部覆盖；只验证查询在指定数据/版本/会话下的可观测行为。

## 3. 首轮验证统计与归因范围

| 首轮输入分流（每条只计一类） | 查询数 | 处理方式 |
| :--- | ---: | :--- |
| 匹配 | | 无独立 Case 文档，不计后续修复积压 |
| 源端负向 | | 默认无独立 Case 文档，不计成功匹配或主归因积压 |
| 非匹配且非源端负向 | | 每条一个 Case Markdown，含前提/读取阻断查询 |

三项合计为本次验证记录总数。保留首轮明确分母的成功匹配率，不以候选结果覆盖。另列其中源成功主范围、环境前提及输出读取异常的数量，不把读取未知当源 SQL 非法。

用本批真实数字在 text 代码框中列出以下关系，所有项须有可核对的来源：

~~~text
验证记录总数 − 成功匹配数 − 默认排除的源端负向数 = 常规应有逐条归因报告数
已生成逐条报告数 + 缺失数 = 常规应有逐条归因报告数
成功匹配率 = 成功匹配数 / 已取得成功源结果的查询数
~~~

首轮失败按转译、目标执行、字段/记录差异、前提及输出读取异常等实际类别进一步统计，解释类别含义与证据限制；错误标签不等于根因。匹配仅表示可用证据下未发现差异，源端负向默认不归因。未知源状态不进入成功率分母，但其非匹配记录仍需按实际范围说明读取阻断。

如果首轮记录重复、统计不一致或缺报告，先明确差额与原因，不改首轮数字来凑等式；输出缺失的查询只有已作为验证记录保留时才计入上述总数。用户明确纳入的负向专项单列数量、理由和额外报告数，不混入默认主范围。

## 4. 调查进度与执行覆盖

- 每条待调查查询的互斥进度：原因已定位、调查未完成、前提阻断、尚未开展；合计等于非匹配且非源端负向数。
- 对每项进度解释已具备的证据和未满足条件，区分根因已定位与类型/排序/边界全部验收。
- 实际对照覆盖的不同 Case 数、独立候选尝试数、原句控制重跑数、失败尝试数与边界数分别统计；同一 Case 可尝试多次，明确各数字之间的关系。
- 批量工具的请求数/完成数/未执行数/工具失败数按请求计，候选执行失败、值差异、类型证据不足和顺序差异为可重叠观察，不是根因数。跨调用统计不同 Case 时按原 Case ID 去重；请求成功完成不等于 Case 原因已定位，不能直接替换调查进度。优先从脚本事实统计填数，再核对逐条覆盖，不凭印象抄数。
- 文档存在不等于调查完成，执行过候选不等于候选通过；未调查项写具体范围，不自行解释为不值得分析。

## 7. SQLGlot 修复任务索引

task 是后续实施和报告单位，Case 是实际证据和回归输入。使用稳定英文编号（如 task-001），按一个可独立说明、验证及审查的行为变化划分，不按 Case、函数、文件或失败数量机械拆分。范围紧密的一组语法/函数及 Parser/AST/Generator 改动可以是一项任务；可独立实现的不同机制应分开。尚需研究的类别不冒充可立即修复任务。

| task-id 与详细条目链接 | 修复目标 | 关联 Case/阶段 | 建议 PR 范围 | 实现依赖/顺序 | 优先级 |
| :--- | :--- | :--- | :--- | :--- | :--- |

在本节为每个可实施任务增加详细条目，不只给 Case 链接，也不新建任务文件。使用如下通用结构，内容取自当前证据：

### <task-id>：<一个具体的行为变化>

- **目标与依据**：当前错误、期望变化、源成功的最小复现和关键证据；说明已复核的 SQLGlot 提交，未查最新 main 则明确。
- **纳入/排除范围**：本任务支持的语法形态、参数/类型/版本条件及明确不解决的问题；区分边界测试与独立功能。
- **实施建议**：实际 Parser/AST/Generator 文件/函数、可复用的 Expression/helpers/能力标志，以及预期修改；不对固定表名或输出值特判。
- **PR 边界与拆分理由**：建议独立 PR，或与哪些紧密相关 task 合并及理由；多文件/多函数不必然拆开，同一 Case/文件不构成合并理由。过大的父问题组说明拆分对应关系。
- **依赖与顺序**：实现必须依赖的 task、共享基础改动和未解决前提；仅共同影响一条 Case 的任务另列为 Case 关联，而非代码依赖。
- **关联证据**：全部有关 Case 链接及其阶段 YAML/JSON；原匹配查询可作为回归输入，不必为其增加 Case 报告。
- **验收**：最小复现、新生成 SQL、正常/NULL/空输入等必要边界、类型/值/顺序条件、SQLGlot 单元测试及相关 dialect/core 回归。说明每个关联 Case 的适用范围，仍有其他问题的 Case 不伪报 MATCH。
- **交付限制**：需补测试/类型/源环境/人工审查的事项，或不能只改 SQLGlot 解决的去向；诊断 unsupported 与补齐可执行转换分别说明。

源端成功证据、实际对照及代码依据支持时才安排修复；仅负向差异或单次值相同不足以提出通用规则。无可实施任务则明确写明，不编造任务或空清单。任务验收不等于整条 Case 全部匹配，也不等于 PR 已提交或会被社区接受。
