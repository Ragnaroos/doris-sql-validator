# PostgreSQL → Doris：归因汇总

参考运行日期：2026-11-13。本文记录固定输入与代码版本下的差异调查，覆盖范围与限制见下文。

## 1. 工作完成情况

先逐条重新读取对应 .out，再决定是否需要独立改写。转译先失败、首轮 JSON 没有源结果的查询，也读取了原 .out。

| 源证据分流（每条只计一次） | 查询数 | 本轮处理 |
| :--- | ---: | :--- |
| .out 记录源端成功 | 1,427 | 241 条首轮成功匹配可简写；1,186 条差异是主评估范围 |
| 源端负向用例 | 298 | 保留完整源 SQL、具体错误和已有目标表现；默认不逐条改写、不安排错误复刻任务 |
| 源端环境/对象前提问题 | 0 | 没有据此排除的选中查询 |
| 已有 .out 的定位/读取异常 | 0 | 全部 1,725 条都成功读取，不是用户没有提供源结果 |

首轮 371 个 MATCH 中，241 个是源端成功结果匹配，130 个是源端负向同类报错。后者不算成功转换。以全部源端成功查询为分母，241/1,427 = **16.89%**；以全部选中查询为分母，241/1,725 = 13.97%。这是补读 .out 后的归因统计口径，没有覆盖首轮报告。

| :--- | ---: | :--- |
| 已确认（当前样本） | 49 | 最新候选在工具已识别的执行、行值、类型声明及必要顺序上对齐；具体原因与未覆盖条件见逐条，不证明全输入同义 |
| 部分确认 | 127 | 已取得具体执行或限制证据，但仍有类型/行值/顺序差异或不足，或只是未改 SQL 的控制重跑 |
| 证据不足 | 28 | 已选择调查，但候选生成、工具校验或结果序列化阻断，缺少完整有效对照 |

四项合计 1,186。本轮选择调查 204 条，176 个不同 Case 有完整关联对照：174 个实际执行原始源 SQL；另 2 个 ORDER BY USING 查询被工具共同使用的 Parser 阻断，只实测了明确保存的 ASC/DESC 规范化源变体，原文成功证据来自 .out。

**本轮没有完成 1,186 条差异的全量根因分析。**298 条负向已按新规则说明，不属于这 982 条未执行积压。没有把原负向查询纳入逐条错误兼容专项；MAKE_DATE 另外补了正常输入成功变体后才建立任务。

## 2. 已定位的问题与具体例子

以下列具体原因与代表证据，不伪造“全部查询已唯一归因”的数量。一个 SQL 可涉及多个问题，不能将任务关联数相加当作缺陷数。

| 问题与原因 | 实际证据 | 能否安排 SQLGlot 修复 |
| :--- | :--- | :--- |
| 误继承 MySQL 数组/NULL 排序限制 | Doris 实测支持 ARRAY 元素构造、NULLS FIRST/LAST，当前 Generator 却在生成阶段拒绝 | 有受限修复方向；解除阻断不等于整个查询修好 |
| 合法 PG 语法被 Parser/Tokenizer 误读 | 0o273 被解释成数值 0 加别名；ORDER BY USING 小于/大于操作符被拒绝 | 需要 PG 解析与字面量回归，不能将成功源 SQL 排除为非法 |
| JSON 文本提取改变含义 | stringy 被生成成带引号的 JSON 字符串；附加路径与 JSON null 也存在差异 | 标量候选已执行；对象 TEXT 的空格差异仍需研究 |
| 命名 WINDOW / 表别名列列表未降级 | 内联窗口和 CTE 列重命名候选可执行 | 需要正确的作用域变换，不能硬编码表字段 |
| NATURAL FULL JOIN 的 Python 异常 | 3 条成功源查询在 eliminate_full_outer_join 迭代 using=None 时 TypeError | 应处理 Doris FULL JOIN 与公共列投影，不仅是吞异常 |
| DISTINCT ON 丢失外层排序 | 首次候选行值与重复次数相同、最终顺序不同；补回外层 ORDER BY 后对齐 | 独立排序任务；本批 USING 端到端回归还依赖 Parser |
| 整数/递归类型与 GROUPING 差异 | 锚点被推成最小整数位宽；整数除法改变窗口分组；GROUPING 多参数直译失败 | 有具体对照，需类型条件；不能无 Schema 将所有除法改 DIV |
| Decimal / Float 尚无可直接应用的通用规则 | AVG 固定 DECIMAL 候选的循环小数末位仍不同；float4 SUM 有显示/驱动/累加疑点 | 先研究精度和编码，不能靠固定 Scale、盲目 ROUND 或 Float 容差掩盖 |
| Doris 缺少原句的直接形式 | Interval、Range/Multirange、部分 PG 函数/XML 等原句控制重跑失败 | 只证明直接形式受限，没有安全模拟时列研究，不说绝对不可能实现 |
| 框架/驱动证据采集限制 | 数组类型声明别名、Range 序列化、校验旧社区 SQL 阻断候选 | 单列框架依赖，不能通过改 SQLGlot 或全部转字符串隐藏 |

例如 PG_INPUT_IS_VALID('asdf','bool') 在 PG **成功返回 false**，仍是主范围；不能因为参数像非法输入就归为负向。源端确实报错的非法 MAKE_DATE 日期则默认排除，再以新正常日期/闰日/NULL 变体建立修复依据。

详见 [逐组详细报告](attribution-details.md)、[候选与工具失败索引](probe-index.json)。本轮没有把缺表/缺数错误当成确定转换缺陷；前后只读核验既有 21 张表/视图的完整记录未变，但 NAME/TEXT 到 VARCHAR(512) 等外部准备映射仍限制类型域。

## 3. SQLGlot 任务与其他去向

[sqlglot-tasks.md](sqlglot-tasks.md) 共 20 项，分别写明源端成功复现、代码位置、实际候选、类型/Schema 前提、反例、测试和验收。其中既有受限修复建议，也有尚需研究的事项，不是 20 个可直接提交的确定通用缺陷。

优先处理有明确阻断的数组构造、原生 NULL 排序、命名窗口、非十进制整数、FULL JOIN 崩溃和 DISTINCT ON 最终排序；再处理类型条件、JSON 路径等相关任务。框架编码、类型别名和候选执行前校验问题单列；类型域限制和缺少对应函数需继续核查安全模拟。

后续由人选择任务并显式调用 pg-doris-fix。本轮没有自动进入修复，没有在默认验证器中加入候选改写或模型调用。临时 AST/生成器候选仅供独立诊断，不是社区 SQLGlot 的默认输出，也不是生产 fallback。

| 统计项 | 数量 | 不能误读成什么 |
| :--- | ---: | :--- |

| 完整 Case 关联对照记录 | 184 | 包含后续候选，不是 184 个不同查询 |
| 其中与社区文本不同的候选执行记录 | 164 | 文本不同不证明同义 |

| 有完整关联对照的不同 Case | 176 | 其中 2 个只实测了标明的源语法变体 |
| 候选行值及重复次数匹配的记录 | 95 | 不表示类型、顺序及全部边界通过 |
| 行值及工具已识别类型/必要顺序均匹配的记录 | 50 | 按执行记录计数，不等于 50 个通用修复，也不证明精度元数据完全齐全 |
| 新边界设计 | 19 | 不是每条原查询都逐条测试 19 个边界 |
| 取得完整记录的不同边界 | 18 | 0o0 AS value 被 PG SQLGlot Parser 阻断，不算通过 |
| 边界完整记录 | 19 | JSON 字符串边界保留了两次尝试 |

首次候选构造有 18 次失败，部分后来有成功的第二候选；工具失败记录 15 条，含 14 个 Case 尝试和 1 个边界。不能把这些次数当成确定缺陷数。

probe 实际重跑 PG、已有社区 Doris（若可生成）、独立候选及重复执行；限制 10 秒/10,000 行，完整有限记录保存在 JSON。没有最终 ORDER BY 时按多重集合比较并保留重复次数，有最终排序时另比顺序。字段类型不同仍继续比较行值，未知类型不算通过；Float 未自动放宽，Decimal 精确比较。

同一个结果行多重集合不代表字段类型/最终顺序相同。重复执行稳定也不证明排序键唯一。数组下界、无界 NUMERIC、完整类型域、Collation、每条 SQL 的全部边界没有全量验证。首轮 241 条成功匹配也没有升级为完整语义证明。

失败证据同样保留：JSON 对象返回 TEXT 仍有空格差异；AVG 的循环小数仍不同；json-text-string 首次错误来自手写候选反斜杠转义，第二次已修正，不能算 SQLGlot 缺陷。
