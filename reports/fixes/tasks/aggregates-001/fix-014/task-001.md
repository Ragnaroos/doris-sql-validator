## 2. 问题依据与实际实现

最小源查询及本轮默认转译：

~~~sql
-- 源SQL
SELECT ARRAY[1::REAL,'1e2'] AS value;
-- fix-013实际生成：目标结果为TEXT数组 ["1","1e2"]
SELECT ARRAY(CAST(1 AS FLOAT), '1e2') AS `value`;
-- fix-014实际生成：目标为FLOAT数组 [1,100]
SELECT ARRAY_MAP(_pg_array_value -> CAST(_pg_array_value AS FLOAT), ARRAY(CAST(1 AS FLOAT), CAST('100' AS DOUBLE))) AS `value`;
~~~

### 2.1 两次失败方案及修正

1. 直接给原文本加FLOAT CAST：原生数组中 `7.038531e-26` 与PG二进制值不同。
2. 先按源位宽算出正确十进制文本、仍用常量FLOAT/整个数组CAST：相同反例依旧失败；因此没有将“精确文本已经算好”当作实际数据库验收成功。
3. 最终采用精确文本 + ARRAY_MAP运行时FLOAT转换，真实数组再取元素提升到DOUBLE比较。原生元素核验通过，原协议显示不同依然保留。

该结果确认的是当前Doris环境的不同执行路径，不宣称已定位当前镜像内部哪一个函数有缺陷。官方master的[FloatLiteral](https://github.com/apache/doris/blob/master/fe/fe-core/src/main/java/org/apache/doris/nereids/trees/expressions/literal/FloatLiteral.java)仅作代码研究线索，不冒充本镜像源码证据。

初版扩大嵌套CAST识别后触发两条嵌套生成递归，已通过父类CAST生成路径修正并添加测试。早期测试另发现旧用例仍把“REAL+unknown文本”列为不支持；现已移除旧排除断言，并用新支持测试替代。最终下述41条和全部测试均在修正后的代码下重跑。

### 2.2 明确限制

- 只处理已确定FLOAT/DOUBLE类型下的有限十进制unknown字面量，不通用重写列、参数、一般表达式或元素已有显式CAST。
- ASCII首尾空白可去除；允许符号、小数点和科学计数法；不将下划线或Unicode数字误认为PG浮点文法。
- 为限制解析工作量，去除首尾空白后的文本超过4096字符拒绝。NaN/Infinity和十六进制本轮也拒绝，即使源成功；并非Doris永久不能模拟。
- 有限值上溢或非零下溢舍入为零拒绝；本轮12条源失败只验证相关保护，不复制PG全部错误兼容。
- 保留负零文本和PG二进制符号；数值等值本身不区分正负零，未验收全部可能的符号观察/运算。
- 混合数组的“其他已知元素本身已被正确求值”仍有前提，两条显式REAL元素CAST反例见第6节。不能把41条通过推广到任意已知表达式。

## 3. 执行方法与比较证据

工作目录为工作流仓库。使用已有解释器、`PYTHONDONTWRITEBYTECODE=1 PYTHONPATH=../sqlglot-experiment:src`，进程内加载原项目.env，不复制/展示凭据。新增变体调用：

~~~python
target = parse_one(source, read="postgres").sql(
    "doris", unsupported_level=ErrorLevel.RAISE
)
pg = execute_query("postgres", source, "dsv_wf_agg001_s01",
                   timeout=10, row_limit=10000)
doris = execute_query("doris", target, "dsv_wf_agg001_s01",
                      timeout=10, row_limit=10000)
checks = compare_probe(pg, doris, source)
~~~

源/目标均各重复一次。类型由PG实际OID和Doris EXPLAIN VERBOSE取得；`_float4/1021`对应FLOAT32数组，`_float8/1022`对应FLOAT64数组。PG多维数组仍用同一元素OID，Doris的维数从实际声明与嵌套结果核对；不把`_float4`与`array<float>`的名字不同误判成能力缺陷。runtime-null-order另有INT4/INT的id字段和明确唯一ORDER BY。

本轮不放宽compare_probe精确比较。`extra_float_digits=0`的源文本与Doris数组文本会损失/显示不同有效位，原生精度另在同一数据阶段用PostgresAdapter只读二进制游标取得。二进制查询也设read-only和10秒超时，不改变主框架的Session政策或.out参考。每个结果叶子按其原数组下标逐个构造Doris原生等值查询，核对NULL、次序和重复；runtime查询逐id核对，并重复一次。数值右侧是源二进制值精确Decimal文本转DOUBLE，不使用Float容差；本轮有限Float32值可精确提升为Double。示例是最终实际执行命令中的一条：

~~~sql
SELECT CAST(p.xs[1] AS DOUBLE) = CAST('7.038530691851209120859188017140306974105991300039164570989669300615787506103515625E-26' AS DOUBLE), CAST(p.xs[2] AS DOUBLE) = CAST('1' AS DOUBLE), p.xs[3] IS NULL, CAST(p.xs[4] AS DOUBLE) = CAST('7.038530691851209120859188017140306974105991300039164570989669300615787506103515625E-26' AS DOUBLE) FROM (SELECT ARRAY_MAP(_pg_array_value -> CAST(_pg_array_value AS FLOAT), ARRAY(CAST('0.00000000000000000000000007038530691851209120859188017140306974105991300039164570989669300615787506103515625' AS DOUBLE), CAST(1 AS FLOAT), NULL, CAST('0.00000000000000000000000007038530691851209120859188017140306974105991300039164570989669300615787506103515625' AS DOUBLE))) AS xs) p;
~~~

该查询两次均返回`[1,1,1,1]`。它是绑定本轮实际生成数组的取证，不是人工替换目标SQL；不能用此真值覆盖主比较器的“不同”。所有41条每个叶子的等值/NULL判断均为真，每端二进制/原始查询重复稳定。

最大DOUBLE另有重要前提：原文本读取器将PG输出`1.79769313486232e+308`解码为float时触发OverflowError；同一原SQL的PG二进制读取确实成功，不能列为源负向。Doris文本也会显示超出Python有限DOUBLE的有效位近似，本轮原生等值仍为真；本报告不修复Adapter/显示规则，保留“源文本解码失败”。
